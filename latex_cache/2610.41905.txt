We compare representatives of six retrieval structures across two multi-tool testbeds: 345 AppWorld queries with expert dependency labels and 103 MCP-Bench tasks over 257 MCP tools. We measure completeness@k, the share of queries whose entire required tool set appears in the top k, alongside the LLM calls, tokens, and latency that each structure incurs at retrieval time. A motivating analysis on all 7,961 ToolRet queries shows that aggregate completeness mixes two regimes: completeness at 10 is .58 to .67 on single-target queries and .08 to .17 on queries with four or more targets, and the ordering of retrievers on single-target queries reverses on multi-target ones. Across the two testbeds, none of the compared structures that is untrained on the testbed and makes at most one LLM call per query completes more than 10\ Tool-using language-model agents increasingly work with tool catalogs that are too large, or too costly, to place in the prompt at every step, so a retriever decides which tools the agent sees . Many requests need several tools, often because one call produces an identifier or credential that another call consumes . For such a request, the retriever has to return the whole required set: if one required tool is missing, the agent cannot carry out that step. This is why COLT framed tool retrieval in terms of completeness and why a recent evaluation of deployed tool search reports completeness alongside recall . We ask which retrieval structures return complete tool sets for multi-tool requests, what each spends at retrieval time to do so, and how each fails when it does not. Existing evaluations do not answer this question, for two reasons. First, tool-retrieval benchmarks are dominated by single-tool queries and report aggregate scores. On ToolRet , 55\ We compare representatives of six retrieval structures on two multi-tool testbeds: 345 AppWorld queries with the expert parameter-level dependency labels of In-N-Out , each needing at least two APIs, and 103 MCP-Bench tasks over 257 tools of real MCP servers, 97 of which need several tools. Each method is run as its authors designed it, the trained set-level methods on each testbed's training queries and the others without training, with one embedding model shared where a method allows it and one LLM for every LLM step. We measure completeness@k and recall@k, the LLM calls, tokens and latency each method spends per query, and, for every incomplete query, which required tools were missed: the target the request asks for, a prerequisite whose consumer was retrieved, or a tool ranked just below the cutoff. Before the main comparison, we use all 7,961 ToolRet queries to show how much an aggregate score conceals; after it, we run the official AppWorld agent on 60 tasks to check whether completeness relates to task success. The study yields four findings. Aggregate completeness on ToolRet mixes two regimes. Completeness at 10 is .58 to .67 on single-target queries and .08 to .17 on queries with four or more targets, while recall at 10 on multi-target queries stays between .41 and .61. bge-base, best or tied for best on single-target queries, is overtaken on queries with two or three targets by both decomposition and COLT's released retriever. This agrees with Zhang et al. and extends their observation to completeness, to queries with up to four or more targets and to trained and graph-based retrievers. On AppWorld and MCP-Bench, flat lexical and dense retrieval, query decomposition, server-then-tool matching and dependency-graph retrieval complete at most 9.6\ The structures fail in different ways. On AppWorld, 58\ With the official AppWorld agent, exposing COLT's top 16 APIs led to success on 21 of 21 tasks where that set was complete and on 2 of 39 where it was not, while exposing the gold API set succeeded on 26 of those 39 incomplete tasks. Tool retrieval benchmarks. ToolRet collects 7.6 thousand retrieval tasks over about 43 thousand tools from many tool-use datasets and evaluates sparse, dense, re-ranking and tool-specific retrievers; it reports recall and completeness at 10 as aggregates. Zhu et al. show that single-label annotations underestimate tool retrievers and expand the labels with equivalent tools. LiveMCPBench and MCP-Bench evaluate agents over many MCP servers, and GatewayBench compares deployed MCP gateways on capability and security. Its gateways implement several of the structures we study: flattened gateways expose every tool, and hierarchical ones let the agent find tools by layered discovery or semantic search during execution. GatewayBench measures each gateway as a product, end to end; we hold shared components fixed and measure the retrieved set and its retrieval-time cost. These benchmarks measure agents or individual retrievers; they do not stratify retrieval completeness by the number of required tools or compare structural families on it. Retrieval structures. Flat retrievers score each tool description against the query, lexically as BM25 does or by embedding both in one space ; Re-Invoke enriches tool documents with synthetic queries , and ToolDreamer instills LLM reasoning into tool retrievers . Decomposition and planning methods split the request into sub-needs before retrieval, trained with reinforcement learning in TOOLQP , prompted zero-shot in the plan-then-retrieve paradigm of Zhang et al. , or combined with tool description augmentation . Hierarchical methods narrow the catalog step by step: AnyTool uses LLM agents over a category, tool and API hierarchy, MCP-Zero matches requested server domains before tools, and A2X builds a service taxonomy with an LLM. Hi-RAG exploits the type, service and tool structure of MCP. Dependency-graph methods add edges between tools: Tool Graph Retriever learns pairwise dependencies, and Graph-of-Skills induces producer-consumer edges from input and output schemas and ranks with personalized PageRank. Set-level methods score tool sets rather than single tools: COLT adds a collaborative learning stage over query, scene and tool graphs, and HYSET predicts query-conditioned hyperedges. Our comparison includes a representative of each of these families. Comparisons of structures. Zhang et al. compare retrieve-then-plan and plan-then-retrieve on ToolBench and find a crossover between single-tool and multi-tool queries that holds across retrieval budgets, registry sizes and two LLMs; the plan step roughly doubles inference cost. Kolluru and Sportsman compare a hybrid ranker with a typed skill graph and explain why graph edges drawn from embedding neighbourhoods cannot extend retrieval reach. Partee et al. evaluate a deployed two-stage tool recommender by completeness at 10 on ToolRet and by billed session cost. Our study differs from these in three respects: it compares six structural families rather than two paradigms or one system, it measures completeness on testbeds with dependency labels, and it attributes each family's failures to missing targets, unrecognized prerequisites or ranking depth. We first ask what an aggregate completeness score on a standard benchmark says about multi-tool requests. We use all 7,961 ToolRet queries over 44,453 tools in 35 tool pools, as counted in the released data , in ToolRet's controlled setting in which each query is ranked only against the tools of its own sub-dataset, with the query text and no instruction. Because this setting differs from ToolRet's full-corpus table, our absolute numbers are not comparable with the published ones. We group queries by their number of distinct target tools: 4,402 have one target, 1,937 two, 1,089 three and 533 four or more. We compare two general embedders , the released first-stage COLT retriever , the decomposition arm described in Section 4.3, and the deterministic variant of Graph-of-Skills. The rest of the paper therefore evaluates on testbeds in which every AppWorld query and 97 of 103 MCP-Bench tasks need several tools. Given a natural-language request q and a tool pool T, a retriever returns a ranked list of tools. Let R be the set of tools the request requires and L\_k the first k tools of the list. Completeness at k is the share of queries with R contained in L\_k ; recall at k averages |R $ $ L\_k | / |R |. We report k = 4, 8 and 16 on the main testbeds and k = 10 on ToolRet, the value ToolRet reports. Several arms return variable-length sets rather than full rankings; their shorter lists count as returned. We compare arms with paired bootstrap 95\ Retrieval-time cost is what an arm spends per query after any index or model has been built: the number of LLM calls, the prompt and completion tokens, and the wall-clock latency of the LLM stage. Training data and index construction are reported separately as requirements rather than as per-query cost. AppWorld. AppWorld is an executable environment of everyday apps. In-N-Out provides expert parameter-level edges between AppWorld APIs, and its release includes AppWorld retrieval queries labelled with the APIs each query calls and, for each of their parameters, the APIs that can produce it. We take a query's required set to be these APIs together with their producers. We use the 345 queries of the official test splits over the 456 APIs of the In-N-Out pool. AppWorld agents always receive the six supervisor APIs that hold the user's credentials, and AppWorld's ground truth excludes them, so we remove them from rankings and required sets before scoring; app login APIs stay required. The remaining required sets have between 2 and 12 APIs . From the In-N-Out labels we form the dependency graph of each query's required APIs: 258 queries form a single connected chain and 87 contain several components with at least one dependency ; no test query needs a single API or only independent APIs. MCP-Bench. MCP-Bench provides tasks over real MCP servers. We list the 257 tools of all 28 servers with MCP-Bench's own collector and use each task's fuzzy description as the query. MCP-Bench has no tool-set labels, so we derive each required set from the tools named in the task's detailed description and dependency analysis, restricted to the task's servers. One task names its tools only by paraphrase and is excluded, leaving 103 tasks . Six single-server tasks name one tool; the other 97 need several. These sets come from the generator's plans, so they are reference sets rather than unique gold sets. We choose one or two representatives per family; Appendix B lists prompts and all changes to the released code. Among methods that implement a family's core mechanism and have usable code, we prefer formally published ones and use a preprint only when no published method can be run. Shared components are fixed across arms where the method allows: bge-base-en-v1.5 is the embedding model of the flat dense, decomposition, server-then-tool and graph arms, and every LLM step uses DeepSeek-V3.2 at temperature 0. Lexical retrieval with BM25 , and dense retrieval with bge-base-en-v1.5 and with e5-base-v2 , over tool descriptions, no training. Decomposition. No trained decomposition method has public code, so we implement the generic form: one LLM call splits the request into sub-requests, each sub-request retrieves with bge, and the per-sub-request rankings are merged round-robin. Hierarchical . AnyTool with the official agent code. AppWorld and MCP-Bench have no level above apps and servers, so apps and servers serve as both categories and tools. We run the search stage only and take the API pool at the official stopping rules ; the downstream solver and self-reflection are not run. The official function schema for API lists declares a null type, which the LLM obeyed by returning nothing, so we replaced it with an array of objects. Server-then-tool. MCP-Zero with its released matcher logic: the LLM writes one request per needed tool naming a server domain and an operation, and the released matcher code keeps the top 5 servers and returns the top 3 tools for each request. The official matcher uses a commercial embedding model; we use bge so that the embedding model is held fixed across arms. Every arm sees the same server text, which is the app or server name only. Dependency graph. Graph-of-Skills with its default construction, including LLM-validated semantic edges built at index time, and with the optional LLM query rewrite off, which is its default in the released code, so it makes no LLM call at query time. Its deterministic variant without the LLM is reported as an ablation. On MCP-Bench, no tool declares an output schema, so the deterministic producer-consumer edges do not form and the LLM adds 254 edges; on AppWorld the default build has 4,935 edges. Set-level . COLT , a published method with released code, retrained with the authors' configuration on each testbed because its set-level stage needs labelled queries on the same tool pool. On AppWorld we train on the 90 official training queries and select checkpoints on the 57 development queries; on MCP-Bench we use five-fold cross-validation stratified by the number of servers. Before retraining we reproduced the authors' ToolBench G2 result with their code . HYSET , a preprint, is run as a simplified variant trained on the same splits: annotation-only training without the execution reward, whose rollout code is not released, and a maximum set size raised to the largest required set . Each arm is used as its authors designed it. COLT and HYSET are supervised methods whose published protocols train on labelled queries over the tool pool they retrieve from, so we train them on each testbed's training queries; the other arms are training-free by design and are run without training. Families without public code are not represented or are represented by a generic reimplementation . The In-N-Out graph retriever takes the gold target API and a missing parameter as input, so it is not a query-level retriever and is not included. We also do not run full exposure, which needs no retrieval but places the whole catalog in the prompt: in the function-calling format, the AppWorld catalog is 64,874 tokens and the MCP-Bench catalog 59,278 tokens under the DeepSeek-V3.2 tokenizer. Both fit in the model's context, so full exposure is feasible on these testbeds; its cost is paid in every agent call rather than once at retrieval, and it is a question of execution cost and tool selection rather than of retrieval completeness. In both, only the exposed APIs can be documented and called, and calls to others return AppWorld's own errors. Exposure A succeeded on 46 of 60 tasks and C on 23 . The difference comes almost entirely from incomplete retrieval. On the 21 tasks where COLT's top 16 was complete, C succeeded on all 21 and A on 20. On the 39 incomplete tasks, C succeeded on 2 and A on 26. Under C the agent took more steps , hit an unexposed-API error in 30 episodes , and used about twice the prompt tokens . The comparison between complete and incomplete tasks is observational, since complete tasks may be easier; but on the same incomplete tasks the gold exposure succeeds two thirds of the time, so the gap is not explained by task difficulty alone. Single-tool evaluation misranks retrievers for multi-tool needs. On ToolRet, the retriever that is best on single-target queries is overtaken on multi-target ones by a retriever trained on tool data and by decomposition. Together with the crossover reported by Zhang et al. , this suggests that aggregate scores dominated by single-target queries should not be used to choose a retriever for agents whose requests need several tools. Completeness on multi-tool requests is bought with either labelled data or LLM calls. On our testbeds, none of the compared structures that runs zero-shot with at most one LLM call completes more than 10\ The failure patterns point to different repairs. COLT's misses are mostly at ranks 17 to 50, so a larger budget or a set-aware reranker over its top 50 could recover many of them. AnyTool's misses are prerequisites of APIs it already found, which suggests completing a found set along producer-consumer dependencies after navigation. Flat and graph arms miss targets, so their problem lies at the first retrieval step. Graph-based expansion helps only when edges exist: MCP tools in MCP-Bench declare no output schemas, so Graph-of-Skills cannot form its deterministic edges there, and its LLM-built edges reduce recall on AppWorld relative to the deterministic graph. Completeness is a useful proxy for downstream success in this setting. Complete sets almost always led to success, and incomplete sets almost never did, while the gold set succeeded on most of the same incomplete tasks. All LLM steps use DeepSeek-V3.2, so the completeness and call counts of the LLM-dependent structures, and with them the trade-off in Section 6 between labelled data and LLM calls, are measured for this one model. Hierarchical discovery depends on model capability more than flat exposure does: in GatewayBench , replacing GPT-5.4 with GPT-5.1 lowered the task success of hierarchical gateways by 37.6 points on average, against 11.9 points for flattened ones. AnyTool's position relative to COLT, which calls no LLM at query time, is therefore tied to the capability of the navigating model. The dense arms, and the decomposition, server-then-tool and graph arms built on them, use base-size embedding models . Larger general-purpose and tool-specific embedding models score higher on ToolRet and its re-annotation , so the 10\ Retrieving a complete tool set decides whether a multi-tool request succeeds in our downstream check: complete sets succeeded 21 of 21 times and incomplete ones 2 of 39 times, and benchmarks dominated by single-tool queries hide how rarely retrievers achieve it. Across six retrieval structures on two multi-tool testbeds, the choice follows from cost: when labelled requests exist for the tool pool, trained set-level retrieval, as represented by COLT, gives the most complete sets at no query-time LLM cost; without them, only LLM-navigated hierarchical search, as represented by AnyTool, reaches a comparable level, at 31 to 38 LLM calls and about five minutes per query; and with at most one LLM call per query, none of the flat, decomposition, server-then-tool and dependency-graph structures completes a tenth of AppWorld requests. BM25 indexes the same tool text as the dense arms, lowercased and split into alphanumeric tokens. bge-base-en-v1.5 encodes tools and queries for the flat bge, decomposition, MCP-Zero and Graph-of-Skills arms, with the bge query instruction ``Represent this sentence for searching relevant passages: ''. e5-base-v2 uses its ``query: '' and ``passage: '' prefixes. Every LLM step uses DeepSeek-V3.2 through the SiliconFlow API at temperature 0; all calls are cached, so reported token counts and latencies are those of the original calls. Rankings are truncated at 50. Decomposition prompt. The single LLM call per query uses the following prompt; the response is parsed as a JSON array, and the query itself is used when parsing fails. Split the user request below into the minimal list of independent sub-requests, one per distinct action or piece of information the request needs . Each sub-request must be a short self-contained sentence. If the request is a single action, return it unchanged as a one-item list. Return only a JSON array of strings. Request: {query} Each sub-request retrieves its top 50 tools with bge, and the per-sub-request lists are merged round-robin with duplicates removed. MCP-Zero. We use the request prompt and matcher logic of the released code : servers are ranked by the similarity between the requested server and the server description, the top 5 are kept, and tools in them are scored by $ $max with the top 3 kept per request. Three changes are made. First, bge replaces the commercial embedding model, so the embedding model is held fixed across arms. Second, neither testbed provides server READMEs, so the server text is the placeholder that AnyTool also receives . Third, MCP-Zero requests tools one at a time during execution, which a retrieval-only run cannot do, so one sentence added to the prompt asks for one request block per needed tool in a single call; the per-request lists are merged round-robin. AnyTool. The official agent code is used unchanged except for three adapters: apps or servers serve as both the category and the tool level of its hierarchy, the GPT calls are routed to DeepSeek-V3.2 through the tools API, and the API-list function schema is changed from a null type to an array of objects. The search stops under the official rules , and the API pool at that point is the arm's output; the downstream solver and self-reflection are not run. Graph-of-Skills. Each tool is converted to a skill document listing its name, description, inputs and outputs; MCP tools publish no output schema, so their output list is empty and no deterministic edge forms on MCP-Bench. The reported arm uses the default build, with full-markdown indexing, LLM semantic completion of input-output edges and LLM-validated relation edges; query rewriting is off, its default. The deterministic ablation disables the LLM steps and keeps everything else, including full-markdown indexing. COLT. On ToolBench G2 we ran the authors' configuration, changed only for speed, and obtained R@5 85.26, N@5 82.78 and C@5 70.85 at the best epoch , against 85.03, 82.54 and 70.10 in the COLT paper. In the released data the tuning and test files are identical, so this epoch selection follows the authors' protocol and uses the test set. For AppWorld and MCP-Bench, the first-stage training loop is reimplemented in plain PyTorch with the same recipe because the authors' training wrapper is incompatible with current library versions; the batch size and number of negatives are adapted to the small training sets , and checkpoints are selected on the development split at k = 10. AppWorld models are trained without the supervisor APIs. HYSET. The simplified variant uses a frozen bge-base encoder, sets the execution-reward weight to zero, and raises the maximum set size from 5 to the largest required set ; other hyperparameters follow the paper's defaults. Rankings list the predicted set followed by the remaining tools in singleton-score order. The released code includes the judge step of the execution reward but not the agent rollouts it scores. MCP-Bench required sets. MCP-Bench provides no tool-set labels, so we derive them. A tool belongs to a task's required set if it belongs to one of the task's servers and is named in the task's detailed description or dependency analysis. Names containing an underscore or hyphen match as whole tokens; plain-word names match only in call context: ``Server:name'', ``name names its tools only by paraphrase and is excluded, leaving 103. The agent is a port of the official simplified ReAct code agent with its prompt file and DeepSeek-V3.2 configuration , run on AppWorld 0.1.3, the version that matches the In-N-Out labels. The supervisor APIs are always exposed. Hidden APIs are deleted from the environment, the API documentation tools list only exposed apps and APIs and return AppWorld's own error messages for others, the prompt's app list is filtered the same way, and the raw request object is removed from the code interpreter so the filter cannot be bypassed.
