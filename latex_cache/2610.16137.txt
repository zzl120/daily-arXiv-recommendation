Existing memory rankers operate in a single pass, scoring each candidate once against the raw query and cutting the ranked list at a fixed top-$K$. The single pass misses memories that the answer needs but that look unrelated to the query on their own, and the fixed cut ignores how many memories the query needs. To address both problems, we propose , a memory ranker that runs as a and loop, following the cognitive theory of memory search: each recalled item joins the cue for the next recall , and recall stops once enough has been collected for the task . For compound cueing, ReMind adds the top-ranked memory to the query context at each step and reranks the remaining candidates under the expanded cue, so that each recall makes the cue more specific and later steps look for what is still missing rather than for what merely resembles the query. For metamemory monitoring, a sufficiency predictor estimates at each step whether the collected memories are enough to answer the query and stops the loop once they are, so that the number of selected memories adapts to each query. In these applications, a helpful response often depends on information the user provided in an earlier session, such as a stated preference~ or a past decision~. To keep this information available, recent work pairs the LLM with a memory system that stores the interaction history as a collection of memories~. At answer time, memories relevant to the current query are retrieved and placed into the model context . Considering the token consumption and the context limit of LLMs, only a small set of memories can be placed in the context~, so the quality of the answer depends directly on which memories are selected~. This selection is far from easy: as the history grows across sessions, the memories of a user become numerous and noisy, and in some scenarios the accumulated history reaches over a million tokens . Finding the few memories that the query needs from such a history is thus a challenging problem~. {./figure/introduction.pdf} Existing memory systems commonly adopt a retrieval-then-ranking pipeline to find the related memories~. Given the candidates retrieved by a lightweight retriever, ranking is the stage that makes the final selection~: it models the fine-grained relation between the query and each candidate, and decides which memories enter the context. Generic rankers~ score each candidate by its semantic similarity to the query; however, a semantically similar memory does not always contain the information the answer needs~: for the query in Figure~, the memories about a self-help book and a travel memoir are close to the query in topic, yet neither of them helps answer the question. Therefore, recent work trains rankers on memory data so that they fit the memory scenario better . These trained memory rankers mainly share the same template: each candidate is scored once against the raw query in a single pass, and the top-$K$ memories are incorporated into the context for response. This template has two problems, and both come from the same root: the ranker scores every candidate with the query alone and never looks at what it has already selected. First, the relevance of each memory is judged in isolation. The memories that a personalized query needs are often related to each other more than to the query itself, and a memory may become clearly relevant only after another one has been selected; a ranker that sees only the query has no way to reach such memories, as with the third author in Figure~ . Second, the ranker has no way to tell when it has collected enough, so the cut has to be fixed in advance. A fixed top-$K$ is too large for a query that needs one memory, filling the context with distracting memories and extra tokens, and too small for a query that needs many, leaving the answer without evidence. In contrast, cognitive models of memory search describe human recall as a recurrent and self-terminating process, in which each recalled item joins the cue for the next recall ~ and the search stops once enough has been recalled for the task . This raises the central question of this work: To answer this question, we propose , a memory ranker that performs ranking as a recurrent and self-terminating loop, as shown in Figure~ . To realize compound cueing, ReMind promotes the top-ranked memory into the query context at each step and reranks the remaining candidates under the expanded cue, so that memories selected early serve as extra cues for memories that the raw query alone cannot match. Each step therefore looks for what is still missing rather than for what merely resembles the query. To realize metamemory monitoring, ReMind carries a sufficiency predictor trained jointly with the ranking objective. At each step, the predictor estimates whether the memories collected so far are enough to answer the query, and terminates the loop when sufficiency is reached. In this way, the number of selected memories is decided by the query itself instead of a fixed top-$K$: the loop runs further when the query needs more memories, and stops early when a few are enough. A simple query thus gets a short context with little noise and few tokens, and a complex query gets all the evidence it needs. Our contributions can be summarized as follows: We identify two limitations shared by existing memory rankers: they fix the ranking in one pass and cut it at a fixed size, so the memories they select never inform the rest of the selection. We propose ReMind, which reformulates memory ranking as a recurrent and self-terminating loop: it repeatedly promotes the top-ranked memory into the query context to rerank the remaining candidates, and terminates the loop through a sufficiency predictor. We conduct experiments on multiple public memory benchmarks, where ReMind achieves the best results compared to state-of-the-art memory rankers. Information retrieval commonly uses an efficient retriever to collect candidates and a more expensive ranker to refine their order~. Among pretrained neural rankers, monoBERT classifies query-candidate pairs with BERT~, while monoT5 generates relevance labels with a sequence-to-sequence model~. LLM-based methods either generate candidate rankings through prompting, as in RankGPT~, or learn to score query-candidate pairs, as in RankLLaMA~, Qwen3-Reranker~, and KaLM-Reranker~. Agent memory systems store and retrieve interaction history to support dialogue across sessions~. For memory construction, MemoryBank combines conversations with summaries~, while SeCom compresses topical segments for retrieval~. A-Mem links related notes~, Mem0 merges extracted facts with existing memories~, and MemInsight adds attributes to guide retrieval~. For retrieval, LD-Agent combines semantic, topical, and temporal signals~, while RF-Mem combines one-shot retrieval with stepwise recollection~. Closer to our work, MemReranker distills LLM judgments for memory ranking~, and QRRanker uses selected attention heads to score candidates jointly~. ConvMemory uses lightweight scoring with an optional cross-encoder refinement stage~, while RMM updates its reranker through reinforcement learning from LLM citations~. In this paper, we propose ReMind, reformulating memory ranking as a recurrent and self-terminating loop. ReMind uses selected memories as cues to rerank the remaining candidates and a shared-backbone sufficiency predictor to decide when to stop. Experiments on public memory benchmarks show that ReMind outperforms general-purpose and memory-specific rerankers. One limitation is that the sufficiency predictor still stops later than it needs to, as in Section~. Closing this gap, for example by calibrating the sufficiency score or by adapting the stopping threshold to the query, is left for future work. ReMind uses two prompts that share the same chat format: a system message, a user message with labeled fields, and an assistant turn in which the model answers or . The relevance prompt scores one candidate memory given the query and the memories already selected, and the sufficiency prompt judges whether the selected memories are enough to answer the query. The number of queries with annotated gold memories is limited in this setting, and prior work trains at a comparable scale~. We follow the same strategy and keep the backbone frozen, training only the LoRA adapters, because full fine-tuning needs more labeled data than this setting provides. The trajectory construction described in Section~ also increases the supervision that a single query provides, because it builds one training instance for every pair of a selection state and a candidate, and it samples $P$ different orderings of the positive memories of each query. A query therefore turns into tens of training instances, and the different orderings act as data augmentation by presenting the same memories in different selection states. ~. LongMemEval evaluates the long-term memory of chat assistants with manually written questions that cover five abilities: information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention. Each question is answered from one or more task-oriented sessions between a user and an assistant, where the needed information is mentioned in passing rather than stated plainly, and most questions draw their evidence from several sessions. The evidence sessions are then placed among a large number of unrelated sessions to form one long chat history. We use the two standard settings released with the benchmark, LongMemEval-S with about 115k tokens per question and LongMemEval-M with 500 sessions per question. We use 60\ ~. PersonaBench measures how well a model understands a user by reading that user's private data. Its data come from synthetic user profiles that cover demographic, psychographic, and social attributes and that are linked to one another in social communities, and the profiles themselves are never shown to the model. Each profile generates three kinds of documents, namely conversations with connected people, interactions with an AI assistant, and purchase histories, in which the attributes surface indirectly and are mixed with sessions that carry no personal information. The questions ask about basic information, preferences, and social relations, and the social questions may take more than one step, such as identifying a relative before recalling what that person likes. We split the dataset into training, validation, and test sets by the personas in a 3:1:2 ratio. ~. ConvoMem is a large-scale benchmark for conversational memory with 75,336 question-answer pairs in six categories: user facts, assistant facts, abstention, preferences, changing facts, and implicit connections. The evidence for a question is spread over one to six messages, so a system has to collect several pieces of the conversation history instead of locating a single statement. The conversations that hold the evidence and the filler conversations come from the same generation pipeline, which prevents a system from spotting the evidence by its writing style. We sample 600 queries similar to PersonaBench and split the dataset into training, validation, and test sets by the personas in a 3:1:1 ratio. Some of these benchmarks contain queries that the user history cannot answer, and such a query has no annotated gold memory. We remove those queries, because a query with no gold memory cannot measure whether a ranker finds the right memories. This also places them outside the scope of ReMind: the loop selects a memory before the first sufficiency check, so it always returns at least one memory and cannot report that the history holds no evidence. Deciding that no memory in the pool can answer the query is a different problem from the one the sufficiency predictor solves, which is whether the memories selected so far are already enough, so we leave it to future work. This section introduces the baselines used in our experiments. This baseline preserves the original order returned by the upstream retriever without applying a reranker. It uses the same candidate pool as the reranking methods. ~. Qwen3-Reranker scores each query-document pair with a Qwen3 language model, using a task instruction to define relevance. It treats relevance as a binary decision and computes the score by normalizing the logits of the and tokens. We evaluate the 0.6B, 4B, and 8B variants. ~. KaLM-Reranker-V1 uses an encoder to precompute passage representations and a decoder to score their relevance to the query through cross-attention. Matryoshka embedding pooling compresses the passage representations, allowing them to be stored and reused across queries. We evaluate the Nano, Small, and Large variants. ~. RankGPT prompts an LLM with a query and a list of candidate passages, asking it to output their identifiers in relevance order without task-specific training. Its sliding-window strategy handles long candidate lists by reranking overlapping groups of passages from the end of the list toward the beginning. ~. MemReranker adapts Qwen3-Reranker to agent memory retrieval using general retrieval data and memory-specific dialogue data. Its training first distills calibrated relevance labels from LLM teachers with a pointwise binary cross-entropy objective, then applies contrastive learning to distinguish hard candidates. We evaluate the 0.6B and 4B variants. ~. QRRanker processes the candidate passages and query together, and derives continuous relevance scores from the attention weights between query tokens and passage tokens in selected attention heads. It trains these heads for listwise reranking, so each passage is scored with access to the other candidates in the input. ~. ConvMemory combines dense embeddings and lexical interaction features with a small convolutional/mixer network to score candidate memories. It is trained with cross-encoder teacher supervision on conversational memory retrieval data. We use the ConvMemory-LoCoMo-MPNet checkpoint. . ReMind-SFT starts from the same backbone as ReMind and is trained on the same queries with the standard reranker recipe, where each query is paired with one positive memory and several hard negatives. In this experiment, answer quality for the fixed-cutoff policy peaks at $K=3$ and decreases for larger cutoffs. Consequently, a query-independent policy cannot effectively use the additional budget because it does not know which queries require more evidence. ReMind instead allocates the number of memories on a per-query basis through its sufficiency predictor. Moreover, among the individually evaluated fixed cutoffs, none reaches the exact-match accuracy of ReMind: the best fixed cutoff obtains 13.58 EM, compared with 14.81 for ReMind. ReMind runs one ranking step for every memory it selects, so it takes more inference time than a single-pass ranker. This section measures this time and compares it with the time that the reader needs to generate an answer. We run ReMind on PersonaBench with the dense retriever for a fixed number of steps from one to five, on a single NVIDIA RTX 4090 GPU. At each step, we measure the time of one forward pass that scores a single candidate given the query and the memories selected so far. The candidates within a step are scored independently of each other, so they can be processed in parallel, and under full parallelism the time of a step equals the time of this forward pass. The cumulative time adds up the step times and is therefore the ranking time of one query in this ideal setting. For reference, we measure the average time that the reader of Section~, Llama-3-8B-Instruct, takes to generate an answer on the same queries and the same GPU. The ranking metrics are computed as in Section~, where the positions after the last step are filled with the unselected candidates ordered by their scores from that step. {8pt} {1.0} {lccc} & Table~ reports the results, and we can draw three conclusions.
