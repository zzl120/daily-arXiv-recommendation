We therefore hypothesised that enriching each chunk with document-level context would improve retrieval performance. To address this, Anthropic's contextual retrieval technique~ was implemented. For each document chunk, an LLM was provided with both the chunk and its parent document and tasked with generating a concise contextual description. The generated context was then embedded together with the original chunk as metadata, enriching the embedding space without modifying the embedding model itself. To further extend capabilities and enable integration with third-party AI agents, we have developed a Model Context Protocol server. The Model Context Protocol, created by Anthropic, provides a standardised interface for connecting large language models with external tools and services~. Snappily described as ``the USB-C port for AI,'' MCP establishes a uniform way to connect LLMs to resources they need, functioning similarly to an API but specifically designed for LLM interactions. This protocol enables seamless scaling, simplified deployment, and asynchronous handling of requests, making it particularly valuable for integration with modern AI development environments such as GitHub Copilot in VSCode, AI chat apps or command-line coding agents . The MCP could also allow future implementations to take advantage of in which an LLM acting as an AI agent may perform repeated vector searches, in combination with additional retrieval tools or other sources of context, until it identifies suitable answers to complex and multi-faceted queries. We implemented the server using FastMCP~, a Python framework that streamlines MCP server development with minimal boilerplate code by providing a high-level, Pythonic interface for building, managing, and interacting with MCP servers. The server is deployed on CERN's PaaS infrastructure, where MCP tools translate user prompts into vector searches against our knowledge base and return structured responses. Prompts and answers are exchanged with the server through streamable HTTP requests, enabling efficient real-time communication. This architecture scales well. The asynchronous nature of MCP tools enables parallel processing of multiple queries, while CERN PaaS can spawn additional server instances on demand to handle increased load. Retrieval-Augmented Generation is a framework that combines a retriever with a generator. The retriever selects relevant passages from a corpus. The generator, typically an LLM, produces an answer to the query using the retrieved passages as context. This architecture addresses two key weaknesses of LLMs trained only on fixed corpora. It gives the model access to up-to-date information and reduces the tendency to hallucinate unsupported claims~. From a user perspective, interaction with a RAG system is indistinguishable from a direct conversation with an LLM as queries are typed in natural language and responses are returned in the same conversational style. Source retrieval and ranking steps are carried out automatically, so the user does not need to manage them, but the underlying sources can still be shown alongside the generated answer. This combination preserves the fluency of an LLM while ensuring that responses are grounded in a controlled corpus of documents. Such grounding is particularly valuable in scientific collaborations, where the majority of documentation is restricted to collaboration members and serves as the definitive reference from detector operations to data analysis. Making this material accessible through RAG ensures that responses remain both trustworthy and verifiable~. One additional advantage of semantic interaction is the potential for non-English queries to be used to search the predominantly English-language corpus. This is particularly relevant for a global collaboration such as ATLAS, where non-native English speakers may face additional barriers when navigating technical documentation. The RAG pipeline follows standard stages. Source documents are organised and into retrievable units, often with additional metadata. These units are embedded into semantic vectors using sentence encoders and stored in a database. User queries may pass through intent routing, safety checks, and reformulation or expansion. Candidate documents are then retrieved, ranked, and passed to the generator, which produces a factually-grounded response as shown in . Variants extend this loop with self-correction, iterative retrieval, or agentic decision-making. A popular strategy that balances granularity and context is the ~, in which a full document or major section is treated as the parent, and the retrievable chunks derived from it are linked as children. This design allows metadata and provenance to be inherited from the parent while retrieval and ranking operate at the level of the children. During generation, the parent document can be passed to the LLM to provide additional context, preserving both traceability and interpretability. Extensions such as GraphRAG~ go further by constructing explicit graphs of relationships, linking not only chunks via citations or hyperlinks but also entities and concepts across documents, enabling retrieval that exploits both document structure and domain-specific connections. Retrieval operates on , which are dense vectors that place semantically similar text close together in a shared vector space. Text is first split into , sub-word units determined by the tokenizer of the model , and a transformer maps each token to its own vector. For retrieval, these per-token vectors are pooled into a single fixed-length embedding representing the whole chunk, with the same model embedding both document chunks and user queries. General-purpose encoders work well, but domain-adapted embeddings can be obtained via fine-tuning on ATLAS-specific material. Smaller models may be advantageous for efficiency and local inference, whereas larger models typically offer richer representations at higher computational cost. Retrieving the correct documents from the database can be limited by the format of the user query. For example, queries that are too short, use synonyms not present in the corpus, or fail to match the phrasing of stored documents lead to poor search results. Query manipulation techniques address this by reformulating the query before a search is performed. Examples include query expansion , prompt reformulation , and synthetic document generation such as Query2doc~ or Hypothetical Document Expansion ~, where an LLM first generates relevant information or a plausible answer that is then included in the retrieval query. In a typical dense retrieval pipeline, the user query is first embedded into the same vector space as the document chunks using the chosen encoder model. Candidate documents are then identified by comparing the query embedding $$ to those of all chunks $_i$, usually with cosine similarity _{ } = _i}{\|\| \, \|_i\|}, or inner-product distance $_{} = _i$ as the similarity metric. This retrieval method exploits the property of high-dimensional vector spaces that two randomly chosen vectors are vanishingly unlikely to point in the same direction. Here, ``dense'' refers to the use of compact, continuous embeddings learned by neural networks. As corpora can contain millions of chunks, efficient approximate nearest-neighbour algorithms and vector stores are used to keep retrieval latency low. Alternatively, exact similarity search can be performed at higher computational cost. Classical ``sparse'' retrieval approaches such as BM25~ rank documents by using term-frequency vectors to match query terms and weight them according to inverse document frequency , which reduces the influence of common words and emphasises rarer, more informative terms. Hybrid systems often combine both dense and sparse methods, improving recall and robustness by covering cases where one method fails and using coincidence between the search types as a sign of high confidence in the relevance of a document. After retrieval, candidate passages must be ranked so that the most relevant evidence is placed within the generator's finite context window. Using increasingly large contexts is both costly and susceptible to context rot, a systematic degradation in model reliability and reasoning accuracy as input length increases~. This phenomenon encompasses the well-documented ``lost in the middle'' effect~, where important details are diluted or ignored when buried among irrelevant material. is a group of algorithms used to combine results from multiple retrievers in an ordered way. This is especially useful when combining results from text and semantic search, where the scoring metrics can have very different scales. This also provides a method for upweighting results returned from both retrievers, which are more likely to be relevant. Ranking maximises relevant signal per token, which is often the dominant cost driver in production RAG systems. A simple cut on the retrieval metric or a limited number of retrieved documents can be used when only one type of search is performed. Reciprocal Rank Fusion ~ is a simple but effective way to combine rankings from multiple retrievers with = _{r R} {k + _{r} }, where $R$ is the set of individual rankers, $_{r} $ is the rank position of document $d$ in ranker $r$, and $k$ is a constant that dampens the contribution of lower-ranked items. With a higher computational cost, cross-encoder re-ranking~ uses a bi-directional transformer to score query--document relevance with high accuracy. Standard RAG architectures operate in a single direction. A query triggers retrieval, and the retrieved passages are passed to the generator for response synthesis. More advanced variants introduce decision points that allow the model to control this process dynamically. The decision points can either be implemented as a static logic chain or as an . In this setting, the agent is an LLM configured to decide whether to search, generate, or call an external tool. The retrieval--generation loop can also be enhanced with self-correction or iterative retrieval. Agentic frameworks such as ReAct~, Corrective RAG ~, and Self-RAG~ enable the model to reason about the quality of the response and to coordinate multiple tool calls or retrieval steps to improve factual accuracy and robustness. Practical deployment is as important as the underlying models. A production RAG assistant requires reliable hosting infrastructure, including vector stores and APIs, and may use specialised accelerator hardware to reduce latency. Integration with existing collaboration tools is also important for adoption. Standards such as the Model Context Protocol ~ provide a mechanism for language models to call external services or to be exposed as callable tools themselves, enabling interoperability across platforms. Evaluating retrieval-augmented generation systems in the context of ATLAS requires a domain-specific benchmark. General-purpose evaluation frameworks such as RagBench~ are valuable for open-domain natural language processing, but they do not capture the specialised terminology, document structures, and interdisciplinary content characteristic of large-scale scientific collaborations. To address this gap, ~, a purpose-built evaluation framework tailored to ATLAS documentation, was developed to provide a reproducible basis for comparison. The benchmark follows a document-grounded synthetic-question generation paradigm, similar in spirit to recent RAG evaluation frameworks such as RAGAS~ and ARES~. Questions are generated directly from the target document corpus rather than curated externally, ensuring close alignment between the evaluation data and the deployed knowledge base. The evaluation is deliberately restricted to non-adversarial scenarios intended to resemble typical ATLAS information requests. Each source document or document chunk is supplied to an LLM together with a persona-conditioned prompt instructing it to pose a realistic question that the passage answers and to compose a reference answer grounded only in the supplied text. The originating document is recorded as the ground-truth source for that pair. Multiple personas simulate different user profiles, including early-career students, experienced analysts, and domain experts. The exact prompts and implementation are distributed with the package~. Candidate pairs are automatically checked for relevance, answerability from the source, and answer correctness, with representative samples inspected manually. Two kinds of question--answer data are used and should be distinguished. For TWiki and Git-based documentation, QA pairs are generated synthetically with the framework above. For ATLAS Talk, real user questions and their corresponding community answers provide higher-quality semantic supervision. Only threads marked as solved or answered are retained, and an additional filtering step removes incomplete or low-quality examples; this filtering was checked by manual inspection of representative samples. The controlled embedding study uses three documentation sources: TWiki, Git-based documentation, and ATLAS Talk. For each source, 4,000 QA pairs are used for fine-tuning, 400 for validation, and 1,000 for testing. The source-specific models therefore use equally sized training sets, preventing corpus size from becoming a confounding variable. The combined model uses all 12,000 training pairs. The 4,000-pair choice was set by the smallest available source and is supported by the scaling study in : the largest gains occur in the first few thousand pairs and diminish beyond approximately 10,000 pairs. A model without fine-tuning provides the baseline. The questions, and hence the QA records, are mutually exclusive across the training, validation, and test partitions. Synthetic, document-grounded questions provide an unambiguous retrieval target and make controlled comparisons practical, but they do not fully reproduce the distribution, ambiguity, or multi-document nature of real user queries. The ATLAS Talk set partly mitigates this limitation because its questions originated with users, while production-log examples in provide a separate qualitative view of deployed usage. Retrieval and generation performance are evaluated with complementary metrics. The metric checks whether the labelled source document appears in the retrieved set; top-$k$ accuracy reports the fraction of questions for which it appears among the first $k$ results. The weighted document-match score additionally rewards correct sources placed nearer the top of the ranking. Lexical metrics, including exact match, F1, and ROUGE~, assess surface overlap between predicted and reference answers, while embedding-based semantic similarity measures alignment in meaning beyond exact wording. These retrieval and text-based indicators are independent of LLM judgement. For the generator comparison in , the framework additionally uses an correctness metric. An independent model receives the question, reference answer, and generated answer and returns a binary judgement of whether the generated answer correctly addresses the question. This metric captures answer quality that surface overlap may miss, but it also inherits the limitations of the chosen judge; the judge model and its settings are therefore reported with the comparison. By combining hybrid retrieval, domain-adapted embeddings, and a reproducible benchmark, it provides source-attributed access to ATLAS documentation while remaining compatible with CERN authentication and data-governance requirements. Its modular design also provides a basis for richer, task-specific services, realising in modern form the vision of shared tools articulated in the 2003 ATLAS collaborative-tools white paper~. Moving generation to open-source models available within the CERN environment~ would remove the current dependence on personal API accounts reimbursed through university grants. The challenge of documentation and information flow in ATLAS has been recognised since the early years of the experiment. The 2003 collaborative tools white paper already warned of the risks posed by fragmented communication channels and poorly integrated documentation~. By 2010, a dedicated study, ``The use of the TWiki Web in ATLAS,'' reported more than 7,000 wiki pages authored by hundreds of contributors, and highlighted both the central role of the wiki and the difficulties of maintaining consistency and quality across such a large, collaboratively written system~. Fifteen years later the scale has multiplied, with more than 35,000 TWiki pages created alongside numerous additional repositories. The 2025 ``Big ATLAS Survey'' confirmed that the fundamental issues remain, with a clear finding being that ~. The problem is therefore not a lack of documentation or effort. On the contrary, ATLAS produces enormous volumes of material and invests significant resources in educating collaborators on how to use its software and computing systems. This includes centralised tutorials, self-guided documentation, and structured training programmes that have been organised regularly since 2004~. However, maintaining this documentation over time presents additional challenges. Information must be continually updated as software and workflows evolve, and undocumented expertise is regularly lost as collaborators leave the experiment or students complete their degrees. Together with the fragmentation of information across many systems, each with its own conventions and limited cross-linking, these factors remain a major barrier to the effective reuse and discovery of existing knowledge. The following section summarises the major platforms currently used to capture and disseminate information within ATLAS. This overview focuses on documentation systems primarily used for off-detector work. In contrast, operations teams rely heavily on electronic logbooks and run-control interfaces, which are outside the scope of this discussion. These teams are already highly effective, as evidenced by ATLAS's strong data-taking efficiency and data-quality performance. For this reason, we do not target operations workflows in the present work, and would only consider extending into these domains once the system has demonstrated consistently robust performance in other areas and reached the level of maturity required for mission-critical tasks. Our emphasis is therefore on the fragmented documentation landscape that supports analysis and software development, where discoverability and unification remain significant challenges. TWiki~ has historically been the main wiki for ATLAS, with over 35,000 pages of notes, instructions, and guides, and is internal to the collaboration. Content is unevenly maintained and written in an inconsistent style. A well-known issue is that much of the material is outdated or no longer accurate, as pages are seldom retired or revised once their authors move on. API access is not available, and the search mechanism is poor. It performs literal keyword matching, largely over page titles, with no relevance ranking, full-text indexing, or semantic matching, so locating the correct page typically requires already knowing its name. A custom back-end was developed by CERN IT for ATLAS, but the flat tree structure makes it difficult to distinguish between private or temporary pages and those maintained by groups. Despite these limitations, TWiki remains the single largest body of ATLAS documentation and is therefore included in . The initial corpus includes pages created at any time, provided that they were modified within the preceding five years . This modification-date cutoff is a pragmatic, precision-oriented choice intended to limit false-positive retrievals from the much larger body of older, unmaintained material. Some older pages retain historical value, but identifying that subset reliably, for example through ownership and link-based signals, would require a dedicated corpus-curation study beyond the scope of the present work. MkDocs~ is a static site generator that builds documentation portals from files stored in a source code management system. They are lightweight documentation portals that are increasingly adopted as a replacement for TWiki. These sites are typically hosted in GitLab~, which makes them easier to version, review, and maintain through standard software workflows, while remaining within the CERN ecosystem. As a more recent alternative to TWiki pages, approximately 10,000 pages of documentation are available. While MkDocs provides a more modern and sustainable alternative, when was first deployed in late 2023 the sites were heterogeneous and decentralised across the collaboration, with limited central indexing, and cross-site searching was not available. MkDocs content is a mix of public and collaboration-internal material. Given its growing role and clean programmatic access, it is included in , with documents collected via the GraphQL API~. The CERN Document Server ~ serves as the archive of internal notes, public papers, and conference reports. Internal notes are often supporting documents for public results and can be ten times longer than the published papers detailing all supporting work and variation tests. Known issues include reliance on inconsistent user-supplied metadata, search functionality that does not effectively cover full text, and incomplete cross-linking between superseded versions. Despite these weaknesses, CDS provides API access to nearly 40,000 internal ATLAS documents, 15,000 conference reports, and 1,500 public papers. CDS therefore spans both public material and collaboration-internal notes. A limited subset of public ATLAS papers and notes has been imported into the databases; the documents included in the present corpus are listed in . For meetings at all levels of the collaboration, Indico~ hosts agendas, contributions, slides, minutes, and recordings or links to recordings stored in CDS. Content ranges from very informal, such as collections of plots, to structured lectures. CERN's Group Management System provides group management and mailing-list functionality, replacing the earlier E-groups service model~. Mailing-list discussions remain a potentially valuable information source, but historical archives are incomplete and are not currently ingested into . Much of the equivalent discussion is increasingly captured by ATLAS Talk. ATLAS Talk is a Discourse-based~ forum platform for support, troubleshooting, and discussion across many topics. Categories can be linked to CERN mailing lists, allowing posts to be distributed by email and replies to be ingested back into ATLAS Talk, thereby bridging forum-style threaded discussion with existing mailing-list workflows. It provides improved search and archiving compared with email and is increasingly used as the central helpdesk for the collaboration, though adoption varies across groups. API access is available on request. Its content is collaboration-internal. Mattermost~ is a CERN-supported real-time messaging platform often used for technical Q\&A and coordination within groups. These conversations contain valuable collaboration knowledge, but their real-time, channel-based format makes them difficult to use as a stable documentation corpus. Instead, is integrated into Mattermost as a conversational interface . JIRA~ is used as an issue-tracking system, for example to request sets of simulated events and to manage ongoing tasks in some groups. Although widely used for debugging and software development, LXR is not integrated with other documentation systems and has no programmatic API, limiting automated retrieval or linking. Glance~ is a metadata and bookkeeping system for membership, appointments, and efforts to publish scientific results, ensuring central records are maintained. Its structured records on roles, appointments, and publication workflows are an attractive source of current collaboration knowledge. Although Glance is not currently ingested into , structured API access has been available since October 2026, making it a near-term candidate once its records are converted into retrievable natural-language descriptions. Documentation is written in many voices, with little editorial oversight, and crucial information is dispersed across platforms that are difficult to search in combination. The result is a paradox of abundance: the necessary information exists, but locating and integrating it into daily work remains a significant bottleneck that reduces efficiency and increases reliance on informal communication. is designed to address this gap by providing a unifying conversational interface across existing systems, complementing rather than replacing the substantial documentation and training efforts already in place. High energy physics experiments such as those on CERN's Large Hadron Collider operate at an unprecedented scale, both in terms of the data produced and the size of the collaboration. The ATLAS Collaboration is one of the largest collaborative efforts ever undertaken in science, numbering about 6,000 members from more than 170 institutions worldwide~, and the experiment generates $ $ petabytes of collision data every year. Supporting this activity is a vast and diverse information ecosystem, including technical reports, internal notes, meeting minutes, presentation slides and recordings, software documentation, monitoring dashboards, and wiki pages. An example is ATLAS TWiki, containing over 35,000 pages written over more than two decades by hundreds of contributors. While this abundance of documentation reflects the collaborative strength of the experiment, it also creates a significant challenge. Information is scattered across many sources, written in many voices, inconsistently maintained, and difficult to search effectively. As a result, even experienced collaborators often struggle to locate the right information quickly, and new members face a steep learning curve in their first years on the experiment. The information retrieval challenge within the scientific community and high energy physics has been recognized for more than two decades. As early as 2003, an ATLAS white paper highlighted the ``opportunities for use and development of collaborative tools'' and warned of the risks posed by fragmented and un-curated documentation~. Two decades later, these concerns remain pressing. The 2024 ``Big ATLAS Survey'' identified documentation and searchability as collaboration-wide concerns, prompting efforts to improve the accessibility and organisation of ATLAS knowledge~. While ATLAS has abundant documentation, its dispersion across many systems and styles makes it hard to access and use effectively. The costs of this fragmentation are high. New collaborators, often PhD students, face a steep ramp-up time to locate the information they need. Established members waste effort re-discovering knowledge or rely on informal channels via personal connections. The collaboration as a whole risks reduced efficiency, creativity, and impact. A unified assistant that can surface relevant information quickly and reliably could flatten the learning curve, free up time for more complex tasks, and improve the collective output of the collaboration. However, such an assistant can only be as good as the documentation it draws upon. The accuracy, completeness, and timeliness of the underlying sources ultimately bound the quality of its responses. Recent advances in artificial intelligence, particularly Large Language Models , provide new opportunities to support scientific work by automating and accelerating information-intensive tasks~. LLMs are neural sequence models based on the attention mechanism using the transformer architecture~. Popularised by general-purpose conversational assistants such as OpenAI's ChatGPT, they have been shown to perform effectively across a range of domains. Notable examples include code generation~, as in Copilot/Codex~, summarisation and synthesis of information across multiple documents~, and the provision of context-sensitive answers to natural language queries by integrating evidence from several passages. However, there are well-recognised limitations when applying LLMs to domain-specific tasks. A central issue is that such models are trained on a fixed snapshot of predominantly public data. As a consequence, they do not incorporate the internal documentation generated within large scientific collaborations. For ATLAS, the majority of relevant material, including technical notes, meeting records, and software documentation, is internal and therefore inaccessible to commercial LLMs during training. Retrieval-Augmented Generation ~ addresses this limitation by coupling a generative model to an , which identifies relevant internal documents at query time and supplies them as additional input, or , for response generation.
