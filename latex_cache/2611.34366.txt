A common way to make long documents searchable at scale is to split them into chunks and index each chunk as a separate record. Chunking can separate text from its identifying details. The indexing challenge is to keep each chunk independently searchable while preserving the context needed to find and rank it. Existing methods either encode that context in chunk vectors or attach it as a text prefix. Context encoded only in vectors is unavailable to text rerankers. Prompted prefixes serve both vector search and reranking, but are costly to generate at indexing time and can underperform contextual encoders. This motivates us to train lightweight language models to generate more effective prefixes at lower indexing cost. To make long documents searchable at scale, systems often split them into smaller units, called ~, that can be stored as separate records and indexed for retrieval~. Retrieval-augmented generation systems are commonly used to retrieve chunks from the index~. The retrieved chunks can be returned directly as search results or used as evidence to answer questions~ and check factual claims~. For RAG over large collections, the index must retrieve the evidence needed for an accurate answer~ while remaining affordable to build and fast to query~. In a pipeline, a system first uses a vector index to shortlist chunks by embedding similarity~. To improve ranking accuracy, the system often uses a reranker to score each shortlisted chunk's text for relevance to the query and reorder the candidates by that score~. However, conventional chunking methods can separate a passage from the context that identifies it~. For example, consider a query for a company's operating income in a particular fiscal year~: the financial table containing the figure may rely on a preceding heading to identify the company and year. If that heading falls in another chunk, vector search may retrieve a similar table for the wrong company or period, and a reranker reading the table alone lacks the evidence to correct the error. To improve retrieval quality at scale, systems must address the fundamental data management challenge of keeping chunks independently searchable while preserving the document context needed to find the right candidates and rank them correctly. {figures/context_travels.pdf} Such a challenge of preserving document context has attracted considerable attention from data scientists~ as well as from AI companies such as Perplexity~, Voyage AI~, and Anthropic~. Two lines of work address this challenge by encoding document context into chunk vectors or preserving it explicitly in text. Figure~ illustrates how these approaches differ in the context available to the vector index and the reranker. The first line of work incorporates surrounding document information into chunk vectors via late chunking~. Building on this design, InSeNT~ trains encoders to distinguish chunks from the same document, and PPLX~ adapts an autoregressive large language model for contextual encoding. These methods can improve candidate selection by changing only the vector representation of each chunk. However, this line of work faces several limitations. PPLX, for example, requires substantial additional pretraining to enable bidirectional attention, adding to the time and computation required to train the encoder. Furthermore, a reranker that reads the original chunk text cannot use document context encoded only in the chunk vector. The second line of work preserves document context explicitly in text. Anthropic's method prompts a large language model to read the source document and generate a prefix for each chunk, supplying the augmented text to both retrieval and reranking~. The prefixes can be reused across queries, a benefit of enriching the index offline~. The upfront cost is the substantial time and computation needed to generate a prefix for every chunk during index construction. Prompted prefixes have also underperformed leading contextual encoders in prior retrieval evaluations~. However, those evaluations primarily examined single-stage retrieval, where chunks are ranked by embedding similarity alone, overlooking multi-stage retrieval. We argue that because an LLM-generated prefix makes context available as readable text beyond the chunk vector, it can be reused across retrieval stages and may offer greater benefits than embedding-only evaluations suggest. In Section~, we use controlled experiments to measure the contribution of prefixes at each stage and demonstrate this potential. To realize this potential at a lower indexing cost, we introduce , a novel reinforcement learning framework for training lightweight language models to write concise, chunk-specific prefixes for both candidate selection and reranking . At indexing time, the trained model generates one prefix per chunk. prepends the prefix to the original text and stores the augmented text and its embedding under the original chunk identifier. At query time, the vector index uses the embedding to select candidates, and the reranker reads the same augmented text to refine their order. During training, frozen embedding and reranking models evaluate each sampled prefix by scoring the augmented chunk against the training query. A frozen judge model checks whether the source supports the information added by each prefix, and a length penalty limits prefix length and reduces competition among chunks from the same document. Evaluating complex relevance models across an entire large corpus is too costly at query time. Modern retrieval pipelines, as supported by frameworks such as PyTerrier-RAG and RAGPerf~, therefore combine fast candidate retrieval with compute-intensive reranking to balance efficiency and accuracy~. Given a query, a retriever first selects a small candidate set using an embedding model, often paired with lexical matching in multi-way retrieval~. While BM25 relies on term overlap and corpus statistics to match exact names and identifiers~, queries and passages frequently express the same meaning with different words. Embedding models address this lexical gap by mapping queries and passages into a shared continuous vector space to capture semantic similarity~. Early architectures build upon bidirectional BERT encoders~, whereas recent models such as E5-Mistral and Qwen3-Embedding adapt pretrained LLMs~. To combine different retrieval signals within a single backbone, M3-Embedding further unifies dense, sparse, and multi-vector retrieval~. Because these retrievers only narrow the corpus down to a candidate set, a reranker must then judge fine-grained relevance by jointly evaluating the query and candidate text~. Cross-encoders such as BERT rerankers and Qwen3-Reranker evaluate individual query--passage pairs independently~, while monoT5 formulates this judgment as relevance-token generation~. Rather than judging pairs in isolation, RankGPT compares a group of candidates through listwise ordering~, whereas RankRAG unifies reranking with answer generation~. Ultimately, the retriever determines which candidates reach the reranker, and the text the reranker reads determines what document context it can rely on to judge relevance. Contextual retrieval mitigates the information loss caused by partitioning documents into isolated chunks. The first paradigm encodes surrounding document context directly into chunk vectors. Late chunking achieves this by encoding an entire source window before pooling token representations within each chunk boundary~. Extending this approach, InSeNT trains contextual encoders using in-document negatives, encouraging models to preserve passage-specific details alongside shared document context~. Adapting this paradigm to autoregressive LLMs requires overcoming causal attention, which restricts tokens to preceding context. PPLX adapts an LLM backbone via diffusion pretraining on roughly 250 billion tokens to enable bidirectional attention, followed by contrastive retrieval training~. Similarly, Voyage-context-3 and Voyage-context-4 provide document-aware chunk embeddings via proprietary APIs~. However, PPLX incurs substantial additional pretraining overhead, and storing context implicitly in vectors leaves downstream components reading raw text---such as rerankers---without access to that context. The second paradigm preserves context explicitly as readable text. Anthropic prompts an LLM to generate a concise prefix situating each chunk within its source document, prepending it to the passage for indexing and reranking~. Because prefixes are materialized at indexing time, they are reusable for retrieval and reranking across queries while remaining directly legible to rerankers.
