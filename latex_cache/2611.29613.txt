Primitive design determines which model changes can be expressed and searched. Agents can design and test new primitives tailored to model, infra and business goals. A agent could also revise its own edit-generation procedures and tools using evaluation feedback, then reuse validated improvements in later iterations toward recursive self-improvement of the editing process . Given goals and constraints stated by engineers in natural language, an LLM coding agent inspects model structure, proposes edits and uses evaluation feedback to refine them ). It works through a sandboxed shell with controlled access to production code repository, training platform, query engine and model artifacts. The agent analyzes weights and evaluates primitives on module groups individually using a development day. It re-measures large effects on separate days and discards edits whose effects reverse sign. Stable effects guide hypotheses and explicit modifications. When a hypothesis identifies a site without specifying values, the agent searches it. To compose edits, it can continue searching with earlier edits in place. Engineers select candidates passing validation protocol in Sec.~ for online tests and decide what ships from those results. If no valid candidates are found, the agent can revisit past hypothesis and results to scan again. It's also possible to include online results to guide future iterations. Before the first scan, the agent built the edit-evaluate engine and checked it against the production evaluator. It registers and deploys edited models after engineer approves. An end-to-end two-tower iteration takes less than 2 hours before finding a handful candidates. Across iterations, the agent evaluated over 2,000 edit configurations and about 190,000 search candidates to achieve the progress shown in Fig.~ . Given the large size of both model and data of production models and evaluators, weight coding maintains its own edit-evaluate engine for faster iteration. The engine runs the production model once on the production evaluator's data and caches embeddings and necessary intermediate outputs. Edits rewrite loaded TorchScript parameters in GPU memory, recomputing only affected modules and their downstream computations. Search directly optimizes the production metric through selected values or a multiplicative scale for each row of a weight matrix. An evolution strategy samples 16 antithetic pairs of Gaussian perturbations per step, scaled by each tensor's root mean square or applied to per-row log-scales . It converts the 32 objective scores to centered ranks and updates with Adam at learning rate 0.03 to 0.05. Dev-day positives are randomly split into disjoint halves and search uses one half. Every 10 steps, the engine evaluates on the other half and retain the best step. Target-model evaluations require forward passes only. To mitigate overfitting or reward hacking, a validation protocol is carefully designed in the loop. We use only dev days to support scanning, edit and search. Then the filter days only discard single edits whose effects reverse sign on dev and filter days. Finally, we also reserve the held-out days for full evaluation and to guide online experiment decision. The held-out days never guide iteration. Following model-editing criteria , we measure efficacy on dev data and generalization on held-out days and metrics and corpora outside the search objective. Specificity checks cover engagement types, fresh, non-fresh and product Pins, distinct top-10 Pins and popular-item share. The evaluator ranks a positive by counting strictly higher candidate scores. A diagnostic edit collapsing item embeddings inflated recall@10 from 0.626 to 0.639, so we also use pessimistic tie-breaking, placing tied candidates ahead of the positive. Finally, the production evaluator scores the edited artifact, which is compared with production tensor by tensor. Our main case is the 147M-parameter Image Search two-tower retriever. The query tower $q_ $ embeds the user, query Pin and context, and the item tower $p_ $ embeds candidate Pin $y$. Candidates are ranked by cosine similarity $s_ = q_ ,p_ $. Both towers start from a cross-surface foundation model and are fine-tuned on Image Search logs ). The query tower processes 35 tokens through a two-layer DHEN ). After an input LayerNorm, layer 0 combines attention and multilayer perceptron branches with a shortcut that mixes all tokens. Layer 1 combines MLP and MaskNet branches with an identity shortcut. In practice, we find that such a cross validation is enough to select candidates for online experiments while early retriever models can still suffer from severer online-offline consistency. The random-DHEN result provides an interesting perspective. Its encoders, output head and item index remain fixed, while searched mixing and normalization parameters establish useful interactions. Together with different edits across the recommendation funnel and online goal adaptation, this supports direct editing as a way to develop model and control behavior. For trained weights, we conjecture that a single training schedule can leave normalization gains, shared offsets and branch strengths poorly balanced for the target task. Edits adjust their relative contributions while retaining representations learned elsewhere. Resetting the L0 gain lowers the in-batch sampled-softmax loss of the retrieval head on the last training day from 1.300 to 1.015. Normalization and branch edits also give similar recall gains on training days and a held-out day a month later. A retrain without weight decay on one-dimensional parameters has LayerNorm gains near one but loses 3.5 recall@10 points under the production evaluator. Mixing-matrix search still adds 16.8 points, compared with 14.1 on production. Small normalization gains alone therefore do not explain the room for weight coding. PinRec benefits from bias edits and interpolation, while resetting the ranker's small LayerNorm gains hurts. Successful edits on the ranker weaken experts relative to their direct path. As a result, useful edits tend to be model-specific while the weight-coding methodology applies generally. It remains an important question to understand how generally weight coding applies to different models, tasks and datasets. Taking a step further, how it complement or even replace the full training, either pre- or post-training. While this work establishes weight coding in real production setting to evolve large-scale models end-to-end with online validation, there are still critical steps to follow before it can become a generally useful methodology in engineering practice. Establishing it as routine production practice requires understanding which modules admit effective control through few parameters and whether successful edits remain useful after model / checkpoint refreshes or data / user distribution shifts. This would help turn the observed progression from local edits to module reconstruction into a more predictable development strategy. Edits need a reproducible lifecycle tied to their starting checkpoint, code, evaluation data, objective and verified artifact. Reusing an edit requires revalidation and attention to dependent artifacts, as the PinRec and ranker examples illustrate. Monitoring and rollback procedures should determine when to retain, revise or retire edits as the model and ecosystem change over time.
