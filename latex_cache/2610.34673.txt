Web-based chat assistants keep a long-term memory of each user's past sessions , so for every request their large language model agent must decide which stored memories enter its limited context . This decision largely determines whether the agent answers correctly, since a context that misses an evidence turn loses 37 to 64 points of accuracy with Qwen for every turn-level design we compare. The decision also runs on every request, so its latency and cost grow with Web traffic, as they do for Web recommenders, and production memory layers are judged by these costs . Three properties make the decision hard. The store is large and keeps growing: in LongMemEval-M, the history of one question holds about 500 sessions and 1.5M tokens , while the answering model in our setting reads at most 2,700 tokens. The budget is per request, so scoring the store with an LLM costs calls in proportion to its size and to traffic. The value is judged on the whole context, since a question whose evidence spans several sessions needs all of it, and feedback arrives for the context and never for a single memory. Memory systems build different structures, such as linked notes, knowledge graphs, temporal hierarchies and fact-augmented keys . Many spend LLM calls to build them, about 440 to 2,270 per question for HippoRAG~2, A-Mem and T-Mem on LongMemEval-S. Without a shared formulation of the decision, it is unclear which component produces the accuracy and what it should cost. Existing selectors also leave evidence out: the four compared methods whose contexts are turns hold all of the evidence for only 0.50 to 0.68 of the multi-session questions. We observe that the three properties are those of recommendation, and we formalize the decision as budgeted slate recommendation. Recommender systems choose a few items from a large catalogue for every request under a latency budget, and they judge the shown set as a whole . In memory selection, the request plays the user, stored turns are the items, and the context is a slate under a token budget. The formalization defines a design space in which every memory system is a point, a cascade of memory construction, recall, ranking and context assembly. Three results about this space reduce design to one problem: within an LLM budget, raise the product of pool completeness and ranking completeness, and fill the slate. We build by solving this problem with no LLM call. A wide pool from two cheap recall channels raises pool completeness, a ranker learned over ten cheap features raises ranking completeness, and the pool size is chosen by their product. A budgeted slate recommendation problem has a distribution of requests $x$, a catalogue $I $ for each request, a monotone set cost $c_x$ on subsets of $I $, a budget $B$, and a slate reward $R $ that is observed only for the slate shown. A policy $ $ maps each request to a slate with $c_x ) B$, and its value is $V =_x $. The cost is the token count of the rendered slate, $c= $, which grows as units are added.
